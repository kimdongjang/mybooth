## 04 직접 재고 관리의 운영 경계 (2026-10-22)

- 사용자 지침으로 납품 승인/예약을 제거했다. 직접 배정과 행사 기간의 운영자 전용 권한이 [현재 정책](../artist-booth-transition/policy-baseline.md)이며 초기 승인 설계를 다시 적용하지 않는다. 부스 참여는 그 부스 운영자에게 총재고 관리 권한을 주며 POS 운영 역할과 별개다.
- 기존 행사 날짜는 저장돼 있지 않아 자동 추정하지 않는다. 일정 미설정은 운영자만 변경하고, 실제 행사 기간을 운영자가 설정해야 작가의 행사 밖 직접 관리가 열린다. 전역 미배정 입고와 행사 배정 변경을 구분한다.
- 공유 원본 매핑/일정/원장을 v2 백업에 보존하지만 다른 부스까지 독립 복원하는 완결 스냅샷은 아니다. 기존 전체 교체 복원·삭제를 막고 별도 복구를 요구한다. 실제 자료 이관/일정 설정/계정 연결/배포는 이번 작업에서 실행하지 않았다.
- 큰 작가 재고의 행사/판매별 전역 집계는 조회 비용이 늘 수 있다. 실제 PostgreSQL 다중 연결 경쟁·부하/교착, 다기기 오프라인·브라우저/모바일·캐시 배포는 공개 전 별도 확인한다. 다른 기기의 미전송 주문은 알 수 없으며 재고 회수/종료 후 늦게 온 판매를 거절하고 큐를 보존한다.

## 03 작가 연결의 운영 경계 (2026-10-22)

- 초대 코드 수신자는 본인 확인 후 연결해야 한다. 이름 검색 자동 연결·미지정 작가 초대·연결 해제/재귀속·물리 프로필 병합은 제공하지 않는다. 잘못 연결하면 원본/감사를 보존한 별도 복구 절차가 필요하다.
- 실제 PostgreSQL 다중 연결의 동시 수락·철회·권한 회수/교착/부하, 두 계정 실브라우저 왕복, 모바일·SW 배포 교체는 미실행이다. 격리 DB 순차 회귀를 경쟁 검증으로 간주하지 않는다. 공개 전 확인하며 현재 실제 작가 계정을 임의 연결하지 않았다.
- 기존 기본 부스 저장 범위로 첫 부스만 생성한다. 여러 부스의 프로필을 한 사용자에 연결할 수 있으나 다중 부스 신규 생성·운영 문맥 선택은 후속 범위다. 작가 개인 전체 백업/복구와 P16 보존 기간·파기는 별도다. 부스 백업의 초대 메타데이터에는 재사용 코드/해시를 넣지 않는다.
- 03 조회/명시적 작업의 최초 요청에서 추가 스키마를 초기화하고 이후에는 테이블 존재 확인으로 DDL을 건너뛴다. 행사별 정산 계산은 큰 자료에서 비용이 늘 수 있으므로 공개 규모의 조회 성능은 별도 검증한다. 옛 세트 스냅샷이 불완전하면 기존 정산 엔진의 fallback 한계도 유지한다.

## 현재 DB와 이관 상태 (2026-10-22 사용자 확인 후속)

현재 서비스는 운영 전이며 실시간 판매·데이터 변경은 없다고 사용자가 확인했다. 기존 7월/같은 계정 12월 자료의 실제 DB 이관은 사용자 요청으로 완료했고 원본·타 계정 지문을 커밋 전후 대조했다. [이관 기록](../artist-booth-transition/02-data-migration.md)이 초기의 미적용 기록보다 우선한다. 아래 동시 운영/실기기·캐시 검증은 공개 운영 전 별도 범위이며 03 진입을 막는 데이터 이관 대기 상태가 아니다.

미지정 상품 4개는 원래대로 보존했으며 프로필 8개는 로그인 계정과 연결하지 않았다. 실제 작가 소유권은 03 연결 시 확인한다. 현재 DB를 무작위 검증용으로 사용하는 것은 계속 피하고, 실패 주입/경쟁 테스트는 별도 DB에서 수행한다.

## 02 호환 기반의 적용 경계 (2026-10-22)

- [02 구현·제한](../artist-booth-transition/02-implementation.md)은 로컬 변경이다. 실제 PostgreSQL 다중 연결·다기기·Android/배포 캐시와 운영 자료 소유권은 별도 검증 대상이며 PGlite 통과로 대체하지 않는다.
- 일반 API 조회로 이관하지 않는다. 미리보기와 현재 비밀번호/원본 지문을 확인한 명시적 이관만 수행한다. 후보 이름은 실제 소유권 증명이 아니며 다른 계정의 동명이인을 자동 연결하지 않는다.
- 이관 계정의 일반 전체 복원·탈퇴·행사 삭제·판매 초기화는 공유 이력 보호를 위해 차단한다. 새 v2 백업은 관계/감사 기록을 보존하지만 일반 운영 복원 workflow를 제공하지 않는다. 소유권 승계·별도 복구/실제 파기 정책은 후속 범위다.
- 구형 캐시에는 작성자 정보가 없을 수 있다. 업그레이드 후 원래 계정으로 온라인 확인이 필요하며, 완전 오프라인의 미연결 캐시는 판매 화면에 임의 귀속하지 않는다. 주문/캐시 자체는 보존한다.
- 수량의 기준은 기존 원본 테이블이며 최초 위치 투영은 재입고/재차감하지 않는다. 창고 실물의 실제 작가/부스 보관 분리는 04에서 확인한다. 불완전 세트·과거 차감·미연결 상품은 예외 보고와 원본으로 보존한다.
- 이관 계정의 매 요청에서 원본/매핑을 재확인하고 레거시 계정 잠금으로 직렬화한다. 계정 규모가 커지면 쿼리/메모리·잠금 대기가 늘 수 있으므로 실제 부하와 잠금 순서를 확인해야 한다. 공개 다중 사용자 운영을 검증한 상태가 아니다.

## 엑셀 편집 경로의 초안 보관 (2026-10-22)

업로드 → 편집 이동 동안 초안/선택 이미지는 컴포넌트 메모리에 유지한다. 새로고침·새 탭·앱 재시작 시 서버 저장 전 초안은 복원하지 않으며, 초안 없는 편집 URL은 업로드 화면으로 이동한다. 일괄 등록 전 화면 이탈은 기존 미저장 확인을 사용한다. 파일 읽기 도중 다른 화면으로 나가면 늦게 끝난 결과로 편집 화면에 이동하지 않는다.

## 정산 마감의 운영 경계 (2026-10-21)

- 지급 완료는 운영자가 송금한 사실을 기록하는 기능이다. 실제 송금/PG 승인과 외부 금융 연동은 수행하지 않는다.
- 마감 전 다른 기기/탭의 판매를 중단하고 모든 거래를 동기화해야 한다. 서버는 다른 기기의 IndexedDB를 조회하지 못한다. 마감/해제 전 revision의 주문은 거절하고 큐는 보존하므로, 남은 요청은 백업을 보존한 상태에서 운영자가 확인해야 한다.
- 기존 개별 작가 차감은 새 행사 비용 분담에 더해 보존된다. 동일 비용을 행사 비용으로 다시 입력하면 중복 차감되므로 마감 미리보기에서 확인한다. 기존 지급이 있는 미마감 행사는 지급액을 보존하며 추가 지급 전 마감이 필요하다.
- 부스 순수익은 아직 집계하지 않는다. 현재 비용 분담은 작가 정산 차감이며, 부스의 수수료 수입과 실제 지출을 구분하는 별도 회계 계약이 없기 때문이다. 여러 행사의 일괄 지급 및 작가별 비용 직접 배분도 이번 범위에 포함하지 않는다.
- 실 PostgreSQL 다중 연결 경쟁·실제 다기기 오프라인·모바일 브라우저·배포 캐시는 별도 확인 범위다. 자동 테스트는 격리 PGlite와 IndexedDB/화면 모형으로 수행한다.

## 계정 백업·재고 확장 후 남은 제한 (2026-10-21)

- 계정 스냅샷은 같은 계정/서버 서명 키의 복원만 지원한다. 이미지 파일과 기기 주문 큐는 제외한다. 키 교체/DB 스키마 형식 변경 시 장기 보관 백업 호환성을 별도 관리해야 한다.
- 서버는 다른 기기의 미동기화 큐를 조회하지 못한다. 복원 후 이전 revision의 쓰기는 차단하지만 각 기기의 새 데이터 로드와 남은 주문 처리는 필요하다.
- 외부 판매는 수량 차감 기록이며 실제 결제 확인/외부 플랫폼 연동/매출 정산은 제공하지 않는다. 파손·로스는 판매 통계에 합산하지 않는다.
- XLSX는 첫 시트, 예시 열 순서, 값 입력을 지원한다. 이미지 파일은 상품 저장 뒤 별도 업로드하므로 실패 시 상품은 유지되며 해당 이미지 재등록이 필요하다. 미확정 배치는 같은 화면에서 내용 잠금 후 같은 요청으로 재확인한다. 탭을 닫으면 선택한 이미지/편집 표는 다시 준비해야 한다.
- 실 브라우저 XLSX 왕복/모바일 시각/파일 선택, 실 PostgreSQL 다중 연결 경쟁, 배포 캐시 교체는 자동 테스트 범위 밖이다.

## 로컬 이미지 저장 경계 (2026-10-21)

- 로컬 이미지 파일은 `.local-data/images`에 남으며 DB JSON 백업만으로 다른 PC의 이미지까지 복원되지 않는다. 서버 종료 후 `.local-data` 전체를 보존한다.
- 업로드와 상품 연결 저장은 별도 단계다. 연결 실패/교체/제거 시 미참조 로컬 파일은 남으며 자동 파일 삭제는 제공하지 않는다. 공개 이미지 URL과 localhost 서버 바인딩을 사용한다.
- 사용자 요청에 따라 실제 업로드/재시작/이미지 연결과 권한 검증은 사용자가 수행한다.

## WithBooth 도메인·브랜드 변경 (2026-10-21)

도메인이 바뀌면 웹 세션·IndexedDB·서비스 워커가 별도 origin에 속한다. 기존 도메인에서 미동기화 주문을 처리하고 새 도메인에서 로그인해야 한다. 자동 브라우저 데이터 이전은 제공하지 않는다. Android 앱 ID와 저장 키는 보존한다. 실제 Vercel 도메인 설정/운영 데이터 변경은 수행하지 않는다.

## 공통 재고 이미지 저장 경계 (2026-10-20)

- 재고 등록과 Blob 업로드는 별도 단계다. 이미지 실패 시 저장된 재고는 유지하며 같은 화면에서 다시 저장할 수 있다. 새로고침/탭 종료 시 선택 파일·업로드 캐시는 사라지므로 파일을 다시 선택한다.
- 이미지 제거는 상품 연결 제거이며 저장소 파일 물리 삭제가 아니다. 업로드 후 연결 실패/파일 교체 시 미참조 Blob이 남을 수 있다.
- 이미지 변경은 공통 정보이므로 연결 행사 마스터에 전파된다. 기존 미동기화 주문 차단/version 검사를 유지하며 과거 판매 스냅샷은 변경하지 않는다. 실제 Blob 업로드/다중 기기 PostgreSQL 경쟁은 미검증이다.

## 그랩 핸들 편집 경계 (2026-10-19)

- 드롭은 기존 행사 소유권/보관/미동기화 주문/expectedOrder 검사를 유지한다. 순서 저장은 놓을 때1회이며 실패 응답 때 로컬 목록을 선반영하지 않는다. 응답 유실로 결과가 불명확하면 새로고침하여 서버 순서를 확인한다.
- Pointer Events/포인터 캡처/elementFromPoint/animation frame을 사용하는 브라우저 기능이다. 핸들만 touch-action:none이며 일반 목록 스크롤/상품 링크 동작은 유지한다. 키보드 대체 조작을 제공한다. 실제 브라우저의 캡처/터치/모바일5열·자동 스크롤 시각 검증은 미실행이다.
- 상품 수30개 내외를 전제로 페이지 나누기를 제거한다. 더 큰 카탈로그의 가상 스크롤은 제공하지 않는다. 기존 운영 날짜/장르는 사용자가 직접 보정하기로 했으며 에이전트의 DB 변경 대기는 종료한다.

## 판매 번호·등록일 보정 운영 경계 (2026-10-19)

- 판매 번호는 행사별 위치이며 상품 삭제 시 뒤 번호가 당겨진다. 영구 식별자는 상품ID/공통 상품 코드다. 번호 변경은 과거 판매를 재작성하지 않는다. 판매 화면의 기존 제작자·종류별 정렬 대신 지정 번호순을 사용한다.
- 재정렬은 행사 행 잠금과 전체 순서 비교로 오래된 동시 편집을 거절한다. 직접 DB 외부 쓰기로 생긴 중복/미번호는 다음 조회에서 정리한다. 실제 PostgreSQL 다중 연결 경쟁과 브라우저 모바일 가로 스크롤·새로고침은 미검증이다.
- 운영 등록일 수정은 에이전트 미실행이며 사용자가 직접 처리하기로 했다. 이전 Vercel 운영 DB 자격증명 로컬 다운로드는 자동 승인 심사에서 차단되었다. 코드/스크립트 검증에는 별도 PGlite만 사용했다. 승인 전 우회 접속이나 운영 변경을 수행하지 않는다.
- 보정 스크립트는 명시적 관리자 범위/빈 등록일/목록 표시 상품에 한정하고 기존 유효 날짜와 삭제 상품을 보존한다. apply 전에 최소 이전값 백업을 저장하며 파일 생성 실패/DB 실패 시 rollback한다. 백업 경로는 .vercel/ 등 gitignore 대상 로컬 경로를 사용하고 연결정보는 로그/문서/커밋에 기록하지 않는다. 실제 실행 전 대상 DB/프로젝트/관리자와 preview 건수를 확인한다.

## 행사 상품 상세 URL 경계 (2026-10-19)

## 총재고·배정 표 편집 경계 (2026-10-19)

- 편집 총재고는 판매분을 포함하는 현재 관리 기준 수량이며 lifetime 누적 입고와 다르다. 감소는 정정으로 기록하고 누적 입고를 줄이지 않는다. 총재고를 늘렸다 다시 줄인 경우 두 원장을 보존한다. 기존 행사 삭제/판매 자료 누락으로 과거 이력을 복원하지는 않는다.

- 모든 소유 행사를 표에 보여주며 신규 연결은 양수 배정 시 생성한다. 새 행사 상품의 초기 판매가는1,000원이며 행사 판매 설정에서 변경할 수 있다. 기존 행사 가격과 명시적인 무료0원 상품은 유지한다. 이미 행사에서 제거한 상품은 배정을 늘려도 활성화하지 않는다. 보관 행사 배정은 줄일 수만 있다.
- 서버는 version뿐 아니라 행사별 stock/initial/revision도 검사하여 판매와 경쟁하는 오래된 계획을409로 거절한다. 클라이언트는 대기 주문을 차단하되 다른 기기 미전송 주문은 알 수 없으므로 각 기기 동기화가 필요하다. 실제 PostgreSQL 여러 연결 경쟁/브라우저 통합 검증은 미실행이다.
- 새 이동 폼은 제거했지만 이전 미확인 요청을 버리지 않는다. 복구 UI가 결과 확인을 마칠 때까지 수정/삭제를 차단한다. 손상된 저장 요청은 자동 삭제하지 않는다.

## 공통 정보 전파·재고 이동 운영 경계 (2026-10-19)

- 공통 이름/메타데이터/이미지는 연결된 보관 행사·제거 상품의 마스터에도 반영한다. 판매 스냅샷은 변경하지 않지만, 스냅샷이 불완전하여 최신 마스터를 참조하는 과거 자료의 표시 제한은 남는다. 행사 가격과 실제 판매 기록은 공통 수정으로 변경하지 않는다.
- 브라우저 대기 주문 차단은 현재 계정의 조회된 행사/현재 기기에 한정된다. 다른 기기 미전송 주문과 대기 주문이 막 생기는 경쟁은 서버에서 완전히 알 수 없으므로 이동·공통 수정 전 각 기기를 동기화한다. 실제 다중 PostgreSQL 연결 경쟁 검증은 미실행이다.
- 새 이동 미확인 요청은 계정/원본/행사별 sessionStorage에 보존한다. 탭 종료/브라우저 저장 삭제 후 클라이언트 자동 복원은 보장하지 않는다. 서버 이동 영수증은 별도 보존한다. 기존 단일 키 대기 요청의 확인 UI도 유지한다.
- 기존 행사 가격/기본 정보 전체 목록 API는 호환을 위해 남기되 연결 공통 필드는 원본으로 보존한다. 임의 판매량 입력은 제공하지 않으며 거래 오류는 판매 취소로 처리한다.

## 행사 장르와 수량 사유 숨김의 경계 (2026-10-19)

- 행사 판매 내역 링크는 사용자의 명시적 이동으로 고정 행사를 바꾼다. 장바구니는 비우며 미동기화 주문은 보존한다. 다른 기기의 대기 주문 및 기존 공통 재고 백업 범위의 제한은 그대로 남는다.

## 공통 재고 도입 후 운영 경계 (2026-10-16)

- 기존 행사의 동명 상품은 같은 실물인지 판단할 근거가 없어 자동 병합하지 않는다. 계정 최초 목록 조회에서 개별 원본으로 채택하며 실제 창고 수량 확인이 필요하다. 복원한 행사도 독립 데이터이므로 원본과 복원본을 동시에 실재고로 합산하지 않도록 운영자가 확인해야 한다.
- 다른 기기의 오프라인 미전송 주문은 서버에서 알 수 없다. 회수 전 모든 기기를 동기화해야 하며 클라이언트 차단은 현재 브라우저의 대상 행사 큐에 한정된다. 동일 행사 다중 기기 초과 판매 위험은 기존과 같다.
- 기존 행사 백업에는 공통 창고/연결/이동 영수증이 포함되지 않는다. 새 공통 재고의 계정 전체 백업·복원/감사 이력 및 동명 원본 병합 UI는 후속 범위다. 행사 복제는 종전처럼 재고0, 판매 없음으로 생성된다.
- 행사 가격·이미지는 행사별 사본이다. 공통 상품 원본의 변경은 기존 행사에 전파하지 않는다. 이미지 신규/수정과 이미지 일괄 등록은 기존 행사 상품 관리에서 제공하며, 채택 시 기존 이미지는 원본에 보존한다.
- 별도 실제 PostgreSQL의 다중 연결 경쟁/DDL 권한/배포 마이그레이션과 실제 브라우저 종료 후 재시도는 추가 검증이 필요하다. 계정 전체 행사 잠금은 정확성을 우선하며 대규모 계정에서는 잠금 범위를 최적화할 수 있다.

## 판매 저장·재전송 기반 개선 후 남은 위험 (2026-10-15)

큐/상태 분리 저장과 취소 시 실패 주문 삭제는 원자 트랜잭션/취소 명령 보존으로 개선했다. Web Locks 안에서 SYNCING 회수, 삽입 순서 전송, 실패 후 중단, 서버 receipt 보존을 추가했다. 신규 거래에는 구성 스냅샷을 사용한다. 아래 기존 분석 중 이 항목들은 이번 변경 전 상태를 설명한다.

아직 계정 소유 필드/마이그레이션·전체 행사 로그아웃 차단·지속 세션·오프라인 최초 준비·관리 큐·로컬 복원은 없다. 서버 기준 상태와 로컬 명령 재적용 병합도 없으며 큐가 남으면 로컬 상태를 보존하므로 원격 변경 표시가 지연된다. 리비전 충돌은 자동 폐기하지 않고 실패 큐를 유지하며 수동 해결이 필요하다. 첫 실패 뒤 후속 전송을 멈추므로 영구 오류 하나가 해당 행사 큐를 막을 수 있다. Web Locks 미지원 환경에서는 안전을 위해 업로드를 중단한다.

기존 스냅샷 없는 판매는 마스터 변경 이후 취소/정산 한계가 남는다. 이미 취소/삭제되어 배포 전에 사라진 판매 ID는 복구할 수 없으며 새 receipts 보호는 배포 후 기록한 ID부터 적용된다. receipts는 프로젝트 삭제 전까지 증가하므로 보존/정리 정책이 필요하다. 다중 기기 초과 판매·실제 PostgreSQL 동시성·실제 브라우저 종료/두 탭 경쟁 검증은 남아 있다. 운영 적용 전 별도 DB에서 CREATE 권한과 경쟁 시 재시도 동작을 확인한다.

## 권장 작업 단위

2026-10-15 프로젝트 관리: 보관은 서버에서 판매·수정을 거절하고 클라이언트/캐시/같은 브라우저 탭에 읽기 전용 상태를 적용한다. 다른 기기의 오프라인 로컬 판매/대기 주문을 조회·잠글 수는 없다. 모든 기기에서 판매 중단·동기화 후 보관해야 하며 해제하면 기존 대기 주문이 재전송될 수 있다. 백업/복원은 서버 저장 자료와 이미지 URL만 포함하고 3MiB 한도다. 이미지 바이너리·미동기화 큐·과거 정리 원본은 제외한다. 실제 여러 연결 동시성/운영 마이그레이션·배포 검증은 남아 있다.

1. **데이터 유실 방지 — P0 완료:** 기본값 추가와 초기화 분리, 판매 보존, 미동기화 주문 차단 및 API 회귀 테스트 추가. 실DB·브라우저 검증은 배포 전 별도 수행.
2. **서버 거래 보장:** 판매·취소 트랜잭션, 재고 동시성, 멱등 키/취소 tombstone, 서버 입력 및 금액 검증.
3. **로컬 복구 보장:** 큐+상태 원자화, SYNCING 회수, 서버 응답 병합, 프로젝트 전환/다중 탭 검증.
4. **과거 기록 보장:** 주문 구성 스냅샷, 취소·제작자 정산 고정, 백업 복원 및 감사 이력.
5. **운영 기반:** 인증 강화, migration, 테스트/타입 검사/CI, 서비스 워커 업데이트 정책.

## 먼저 확정할 업무 규칙

- 인터넷 없이 여러 기기에서 같은 재고를 팔 때 허용할 초과 판매 및 충돌 해결 방식.
- 현금/계좌이체의 실제 수령 확인 시점과 취소·환불 상태를 별도로 관리할지 여부.
- 무료 상품, 세트 할인 배분·반올림, 제작자 정산 기준.
- 기본 상품 업데이트는 기존 항목을 덮어쓰지 않고 누락만 추가한다. 별도 메타데이터 갱신 정책과 판매 기록 보존 기간은 후속 확정이 필요하다.
- 신규 가입 공개 여부, 행사 직원의 공동 프로젝트 접근/권한 모델. 현재는 관리자별 프로젝트 소유만 구현되어 있다.

기존 12월 행사 정리는 지정된 admin 행사 ID 두 개에만 적용하고 pos_event_archives에 원본을 보관한다. 표식 삭제는 재정리를 유발하므로 보관 정책이 필요하다. dataRevision으로 옛 POST를 차단하며 로컬 미전송 주문은 ARCHIVED로 보존한다. 복원 UI 및 실제 브라우저 전환 검증은 남아 있다.

이메일 가입은 형식 검증과 DB 고유 제약을 적용하지만 소유 확인 메일은 발송하지 않는다. SNS 로그인 도입 전 provider 사용자 ID 기반 연결, 이메일 미제공 처리 및 인증된 기존 계정의 명시적 연결 절차가 필요하다. 이메일 일치만으로 계정을 연결하지 않는다.

## Android 앱과 웹 업데이트 경계 (2026-10-20)

앱 삭제/데이터 삭제는 미전송 IndexedDB 주문을 잃게 한다. 브라우저와 앱 저장소는 분리된다. 최초 온라인 로그인/행사 준비가 필요하며 토큰은 앱 WebView localStorage에 평문 보관한다(Android 앱 백업 비활성화). OTA는 동일 HTTPS origin과 checksum/네이티브 버전·계약을 확인하나 서버 신뢰와 배포 계정 보안에 의존한다. IndexedDB 파괴적 마이그레이션은 번들 복구와 호환되지 않으므로 별도 이전 설계가 필요하다. 이전/실패 번들 보존에 따른 저장 공간 정책은 후속 범위다. 실제 Android WebView 통신/종료/오프라인 재실행/OTA 복구/파일 업로드·백업은 출시 전에 실기기 검증한다. 자세한 절차는 [Android 문서](../android.md).

## 회원 탈퇴·데이터 이전 (2026-10-21)

탈퇴는 서버 계정 자료를 제거하지만 Blob 이미지와 각 기기의 IndexedDB 주문/캐시는 삭제하지 않는다. 접근 차단 표식으로 기존 ID를 보존하므로 같은 ID로 재가입할 수 없다. 다른 기기의 미동기화 주문은 서버가 확인할 수 없다. 전체 데이터 이전은 docs/data-portability.md의 검토 단계이며 기존 행사 백업은 공통 창고·행사 간 연결·이미지 파일 자체를 옮기지 않는다. dev:remote에서는 로컬 POS/인증 API 변경이 원격 서버에 반영되지 않는다.
## 대시보드·수익현황 집계 범위 (2026-10-21)

대시보드 행사 요약은 서버 동기화 완료 주문만 집계한다. 수익현황 상세는 선택 행사의 기존 로컬 투영을 사용하므로 미동기화 주문이 있으면 서버 집계와 일시적으로 다를 수 있다. 비용·원가·실제 입금 확인 데이터는 없으며 판매액을 순이익으로 해석하지 않는다. 대시보드의 공통 재고 집계는 재고 목록과 동일하게 삭제되지 않은 원본 범위다. 수익현황의 행사 선택은 판매 컨텍스트도 전환하며 기존 장바구니 초기화 규칙이 적용된다.
## 계정 대시보드 합산 한계 (2026-10-21)

작가 고유 ID가 없으므로 이름이 같은 작가는 합쳐지고 이름이 바뀌면 별도로 표시된다. 과거 스냅샷 없는 거래는 기존 정산과 동일하게 최신 상품/세트를 참조하는 한계가 있다. 상품명 Top5는 옵션/중복 ID를 이름으로 의도적으로 묶은 조회이며 데이터 병합은 하지 않는다. 정산 완료/비용/원가/실제 입금 및 현금 인출 데이터가 없으므로 미완료 정산 수·순이익·현금 보유액은 추정하지 않는다.

보관은 기존 archivedAt 상태이며 별도 행사 종료일이 아니다. 재고 경고 임계값은 활성 행사 재고3개 이하이며 미분배가 있는 경우만 표시한다. 미동기화 요청 수는 현재 기기에 한정되며 취소 명령도 포함한다. 재고 막대는 활성 공통 재고 목록의 실제 판매 이력과 현재 수량 기준이며 과거 분실/정정 등을 판매로 추정하지 않는다. 행사별 순차 snapshot 요청은 같은 DB 순간의 원자 snapshot이 아니며 새로고침으로 갱신한다. 행사 수 증가 시 집계 전용 API의 검토가 필요하다.
## 정산 원장 운영 범위 (2026-10-21)

지급 기록은 실제 계좌이체가 아니며 현금/계좌 매출도 현재 현금 잔고·실입금 확인을 의미하지 않는다. 작가ID가 없어 같은 이름은 합쳐지고 이름 변경은 별도 작가로 취급된다. 수수료는 자동율 계산 대신 작가·행사별 항목 금액을 입력한다. 운영비 차감 합계는 순이익이 아니다. 기간 필터는 판매 집계에만 적용하며 정산 잔액은 전체 기간이다.

판매 취소/전체 판매 삭제 이후에도 지급 원장은 보존하며 초과 지급과 판매액 초과 차감을 표시한다. 지급 취소는 실제 송금 반환이 아닌 원장의 보정이다. 다른 기기의 미전송 주문을 알 수 없어 모든 기기의 동기화가 필요하다. 행사 삭제는 원장도 CASCADE 삭제한다. 기존 행사 복제·백업/복원은 원장을 포함하지 않으므로 원장 보존에는 DB 백업과 별도 CSV 정산서 보관이 필요하다. 공개 공유 링크/이미지 발송·XLSX는 이번 범위 밖이며 작가별 CSV를 제공한다. 요청 영수증·지급 이력의 자동 삭제 정책은 없다. 실제 PostgreSQL 여러 연결 경쟁과 모바일 실기기 검증은 별도 범위다.

## 06 구형 쓰기 종료의 적용 경계 (2026-10-22 후속)

서버는 기기의 IndexedDB·설치된 클라이언트를 볼 수 없다. 종료 전 현재 기기 큐 검사와 소유자의 전체 기기 확인을 받지만 원격 기기까지 자동 검증하지는 않는다. 누락한 구형 큐는 410 후 FAILED로 보존되며 뒤의 취소도 대기한다. 기존 자동 재시도는 유지되므로 소유자가 호환을 복구하고 원래 기기/계정/행사에서 같은 원본을 동기화해야 한다. 저장소 초기화나 주문 재작성으로 우회하지 않는다.

`admin_id`는 저장/잠금/백업에서, 이름 별칭은 기존 원장/마감에서 아직 참조한다. ID 기반 요청 종료를 물리 스키마 제거로 해석하지 않는다. 현재 열·키 삭제나 과거 백업 복원으로 되돌리면 새 거래가 손실될 수 있다. [06 기록](../artist-booth-transition/06-implementation.md)의 정책 복구를 사용한다. 실제 DB 종료·다중 연결 경쟁·실다기기와 배포 검증은 미실행이다.

## 06 실제 적용 이후 남은 경계 (2026-10-22 추가 후속)

기존 admin 부스에 종료 정책을 실제 적용했고 사용자 기기 확인·백업/독립 재현/커밋 후 원본 및 다른 계정 대조를 완료했다. 앱 배포나 실기기 검증은 수행하지 않았다. 과거 배포 코드가 새 정책을 준수한다고 간주하지 않는다. 공개 전 서버와 클라이언트를 같은 계약으로 반영해야 한다. 보존 중인 `admin_id`·정산 이름 별칭을 삭제하려면 현 재고/원장/백업 참조를 먼저 교체해야 한다.

행사별 부관리자 요청은 부스 전체 권한으로 처리하면 안 된다. 기존 booth manager/seller는 여러 행사에 접근하는 별도 역할이다. 메뉴만 숨기거나 `manage` 조회를 참여 작가에게 열면 타 작가 정산·판매가 노출될 수 있다. [메뉴 가이드](../artist-booth-transition/07-navigation-and-permissions.md)의 행사 범위·본인 응답·서버 권한 분리를 다음 구현의 필수 조건으로 둔다.

## 공통 데이터 계층 적용 경계 (2026-10-23)
실제 업무 쓰기는 아직 공통 큐에 등록하지 않았다. 개인 재고/수익 등은 직접 API 방식을 유지하며, 순서·멱등성·공유 재고·충돌 해결 어댑터를 먼저 검증해야 한다. 판매 큐를 중복 등록하지 않는다. 서버 권한 회수 시 캐시는 표시를 차단하되 미전송 원본/명령을 보존한다. 전체 행사 선다운로드·웹 지속 세션·앱 종료 후 동기화는 미구현이다. [공통 계약](local-first-data.md)을 따른다.

## 운영자 재고관리 허용의 적용 경계 (2026-10-23)

기존 무조건 공동 관리 표현은 최신 재고 정책의 작가 설정·확인된 참여 부스 조건으로 대체한다. 기존 계정/참여는 첫 열 추가 시 현재 관리 상태를 보존하며, 새 검색 참여는 작가 확인을 요구한다. 운영 DB에 직접 열을 추가하거나 배포한 것은 아니다. 실제 브라우저 설정 전환·계정 왕복·실 PostgreSQL 다중 연결과 캐시는 격리 DB 검증과 별도로 확인한다. 기존 주문은 위임 해제 때문에 삭제/성공 처리하지 않으며 판매·취소 권한은 유지한다.

## 제작자 검색·임의 프로필 연결 경계 (2026-10-23)

화면 명칭은 제작자이며 내부 artist/owner ID와 저장 계약은 유지한다. 임의 프로필을 기존 계정에 연결해도 서로 다른 원본 상품/프로필을 물리 병합하지 않는다. 행사 참여 추가(role:none)는 판매 역할이나 총재고 위임을 자동 부여하지 않는다. 검색 등록한 타 계정의 재고를 다루려면 기존 참여 확인과 본인 설정 조건을 충족해야 한다. 계정 연결/행사 제작자 매핑으로 과거 판매 귀속을 재계산하지 않는다. 실제 브라우저 중첩 dialog·실계정/다중 연결 검증은 격리 회귀와 별도로 남긴다.

## 재고 계획 저장·종료 회수 경계 (2026-10-23)

개인 상세의 여러 값은 saveArtistStockPlan 단일 트랜잭션으로 저장하며 부분 저장으로 회수만 남거나 총재고만 늘어나는 것을 방지한다. 회수는 남은 실물 범위이며 이미 판매/소비된 수량을 줄일 수 없다. 종료 행사는 계획 UI에서 증가·직접 편집을 잠그고 잔여 회수만 제공한다. 마감/권한/위임 조건은 그대로 적용하므로 정산 마감된 행사의 회수를 위해 마감을 자동 해제하지 않는다. 판매 이력·원본 소유권·다른 행사 배정을 총재고 변경으로 재작성하지 않는다. 실제 다중 연결·오프라인 지연 판매·실기기 sticky/카드/dialog 확인은 격리 회귀와 구분한다.


## 행사 단위 백업·새 행사 복원 경계 (2026-10-23)

행사 복원은 기존 행사를 덮어쓰지 않으며 별도 미연결 제작자·독립 재고로 가져온다. 원본 행사와 복원 행사를 동시에 실물 재고로 취급하면 수량/판매가 중복 해석될 수 있으므로 자동 원본 병합이나 기존 행사 삭제는 하지 않는다. 복원은 자료 확인용 판매 종료 상태이며 정산 마감/지급 정보도 원본대로 유지한다. 이미지 URL의 대상 파일 존재·접근 가능 여부는 복원으로 보장되지 않는다. v1에는 비용/정산 정보가 없고 v2만 포함한다. 행사 삭제는 아래 후속 기록의 내부 이력 보존 방식을 따른다. 다른 기기의 미전송 주문은 서버 백업으로 알 수 없으며 기기별 동기화가 필요하다. 실제 PostgreSQL 다중 연결·실기기 파일 다운로드/선택·브라우저 접근성·배포는 격리 기능 테스트와 구별한다.


## 행사 삭제와 제작자 삭제의 보존 범위 (2026-10-23 후속)

전환된 행사 삭제는 운영 목록에서 제거하는 삭제 표시다. 공통 재고 하한과 정산을 지키기 위해 과거 판매/소비·지급 원장은 물리 제거하지 않는다. 남은 재고는 허용된 위임 범위에서 자동 회수한다. 행사 삭제와 계정/프로필의 물리 삭제는 같은 동작이 아니다. 제작자 삭제는 현재 행사 연결 해제이며 공통 재고의 소유권·다른 행사와 과거 귀속을 변경하지 않는다. 운영자 고유 부스 권한은 행사 권한 드롭다운으로 강등하지 않는다. 타 기기의 미동기화 주문은 서버가 미리 알 수 없고 삭제된 행사 주문은 404로 거절된다. 미전송 원본은 자동 폐기하지 않는다. 실제 다중 연결·타 기기/오프라인 왕복·브라우저 dialog 검증은 격리 테스트와 구분한다.
