# 06 구현 결과 — 부스별 구형 쓰기 종료·복구

최신 후속: 사용자 확인 후 기존 admin 부스의 실제 종료/보존 대조를 완료했다. [실제 적용 기록](06-data-retirement.md)이 아래 최초 로컬 구현 시점의 '실제 적용 전' 기록보다 우선한다. 저장 열·별칭의 물리 삭제, 새 메뉴/행사별 대리 권한 구현 및 앱 배포는 미완료다. 메뉴 후속은 [재배치 가이드](07-navigation-and-permissions.md)를 따른다.

2026-10-22. 05 기업 모드는 사용자 요청으로 제외한다. 종료·복구의 로컬 구현을 완료했으며 실제 DB 정책/DDL/자료 삭제·계정 연결·배포는 실행하지 않았다.

## 적용한 계약

- `api/lib/contractRetirement.js`, `api/booths.js`: 소유자만 `GET /api/booths?contracts=legacy&boothId=...`로 매핑 진단을 조회한다. 행사-부스, 상품 귀속, 재고 소유자, 기존 정산/마감 행의 수취인 매핑을 원본과 대조한다. 원본 지문·매핑·정책 버전의 진단 지문을 반환한다.
- `POST /api/booths`, action `changeLegacyContracts`: payload의 `boothId`, `requestId`, `version`, `expectedFingerprint`, `queuesChecked`, `closed`, 현재 `password`를 받는다. 소유자/활성 권한과 비밀번호를 검증한다. 종료는 매핑 완전성과 전체 기기 확인을 요구하고 지문/버전 불일치는 409다. 같은 ID/내용은 같은 영수증을 반환하고 같은 ID/다른 내용은 거절한다. 비밀번호는 영수증/백업에 저장하지 않는다.
- `pos_booth_contract_policy`, `pos_booth_contract_commands`: 종료 여부/버전과 감사 영수증만 추가한다. 관리자/부스 잠금과 트랜잭션 안에서 정책·영수증을 원자적으로 저장한다. 테이블이 없거나 해당 부스가 종료하지 않았으면 기존 동작을 유지한다.
- `api/lib/boothFoundation.js`, `api/pos.js`, `api/settlements.js`: 종료한 부스의 POST는 명시적 `boothId`가 필요하다. 판매/취소는 기존 actor 바인딩과 `protocolVersion:2`를 요구한다. 차감/지급/지급 취소는 `recipientId`가 필요하고 `creator` 쓰기 키를 거절한다. 구형 계약은 410, GET은 유지한다. 작가 재고/초대 API는 이미 부스·소유자 ID를 검증하는 별도 계약이다.
- `src/utils/apiContractContext.js`, `src/App.jsx`: 현재 로그인 토큰과 성공한 POS 조회의 부스 범위로 신규 직접 요청만 보완한다. 계정 전환 시 이전 범위를 폐기하고 호출자가 명시한 범위는 보존한다. 프로필/인증/탈퇴에는 범위를 주입하지 않는다. 저장된 주문 동기화는 이 helper를 거치지 않는다.
- `SettlementEditor`, `EventSettlementPanel`, `RevenuePage`: 수취인 매핑으로 ID를 보내고 요청에서 이름 키를 제거한다. 표시명·과거 집계·마감 스냅샷은 변경하지 않는다. 미이관 계정은 기존 계약을 유지한다.
- `ContractRetirement`, `AccountPage`: 마이페이지에서 소유자만 진단/현재 비밀번호/전체 기기 확인을 거쳐 종료·복구한다. 종료 전 현재 기기 미전송 주문을 검사한다. 중복 클릭을 잠그고 응답 유실 시 요청 ID/내용을 고정하여 재확인한다. 서비스워커는 v134다.

## 종료 전 확인과 복구

1. 별도 검증 DB에서 최신 클라이언트 판매/취소·정산과 백업을 확인한다. 기존 실제 7월/12월 자료는 [02 이관 기록](02-data-migration.md)을 보존한다.
2. 모든 브라우저/앱에서 원래 계정·행사로 미전송 주문을 동기화하고 최신 클라이언트를 사용한다. 서버는 기기 큐를 볼 수 없으므로 체크박스는 소유자의 확인이며 자동 증명이 아니다. 오래된 백업 사용 여부도 대조한다. 운영 전이라는 이유로 큐가 없다고 추정하지 않는다.
3. 부스 소유자가 마이페이지의 구형 쓰기 계약에서 ID 매핑을 확인하고 종료한다. 실제 DB에 대한 조작은 이번에 실행하지 않았다. 판매가 일어나 지문이 바뀌면 새 진단을 확인해야 한다.
4. 구형 기기의 410이나 누락한 큐를 발견하면 소유자가 현재 비밀번호로 **구형 쓰기 호환 복구**를 실행한다. 정책/버전만 바꾸고 새 거래·재고·정산을 과거 백업으로 덮어쓰지 않는다. 복구에는 빈 큐 확인을 요구하지 않는다.
5. 원래 기기/계정/행사에서 큐를 재전송한다. 410 주문은 기존 `FAILED`로 남고 뒤의 취소는 대기한다. 기존 자동 재시도는 계속되므로 원인을 해결해야 한다. 주문 삭제·재작성·저장소 초기화 없이 모두 동기화한 뒤 새 진단으로 다시 종료한다.

## 유지하는 참조와 물리 삭제 조건

| 참조 | 유지 이유 | 제거 전 필요한 작업 |
| --- | --- | --- |
| `admin_id`, `legacy_admin_id` | 원본 저장/조회·재고 보관 계정과 잠금 범위 | 부스/소유자 ID 기반 물리 스키마 이관, 원본 대조, 타 계정 격리·복구 검증 |
| `legacy_creator`와 기존 정산 이름 키 | 수취인 ID를 기존 원장에 연결하고 마감/비용 숫자 보존 | 원장·비용 참여자·영수증·마감 원본을 잃지 않는 새 저장 형식과 읽기 어댑터 |
| 상품/재고/행사 ID 매핑 | 과거 거래·재고 링크·작가 귀속 조회 | 모든 조회/변경/백업 참조 대체와 이력 합계·귀속 대조 |
| 이미지 보관 계정·기존 URL | 이미지 경로·원본 편집 권한 | 이미지 참조/권한 이전 검증; 파일 정리는 별도 |
| v1/v2 백업 읽기·원본 큐 payload | 이전 파일 복구·주문 멱등성 | 지원 파일 변환/왕복 대조, 모든 기기 큐 해소·버전 확인 |

부스 종료는 요청 호환 종료이며 저장 형식 제거가 아니다. v2 백업에 계약 정책/영수증을 함께 보존한다. 기존 v1 왕복과 이관 계정의 전체 교체 복원 제한은 유지한다. 과거 거래·감사 기록은 삭제 대상에 포함하지 않는다.

## 검증 결과

최종 실행 결과는 [하네스 검증 기록](../harness/validation.md)의 06 항목을 따른다. 격리 PGlite의 종료/복구·권한·비밀번호·지문·멱등성·실패 롤백·백업, fake-indexeddb의 410 주문/취소·투영 보존·동일 재전송, 신규 요청의 계정 범위·수취인 ID 변환을 자동 검증했다.

실제 PostgreSQL 다중 연결 경쟁/DDL, 실제 브라우저·모바일의 토큰 전환/주문/복구, 다른 기기의 큐 확인, Android와 배포 캐시는 미실행이다. 기존 실제 DB를 검증용으로 사용하지 않았다. 물리 스키마 제거와 실제 부스 종료를 완료로 표시하지 않는다.
