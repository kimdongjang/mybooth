# 06 실제 자료의 구형 쓰기 종료 적용

2026-10-22 후속. 사용자가 **모든 기기의 미전송 주문이 없고 앞으로 최신 버전만 사용함**을 확인한 뒤 기존 자료가 있는 `admin` 기본 부스에 종료 정책을 적용했다. 다른 계정 부스에는 적용하지 않았다. 코드 배포·서버 재시작과 DB 정책 적용은 구분한다.

## '실제 적용 완료'의 의미

이 기록의 완료는 **구형 쓰기 종료 정책을 실제 DB에 저장하고 기존 자료 보존을 대조했다는 뜻**이다. 작가 중심 구조의 DB·API·화면·배포 전체 전환 완료를 뜻하지 않는다.

기존 자료에는 앞선 02 단계에서 부스/행사/작가 후보/재고 소유자 관계를 추가했지만 원본 저장 테이블과 ID는 유지한다. 작가 후보를 실제 본인 계정과 연결하지 않았고 기존 재고 화면·엑셀·개인 수익·행사별 대리 권한과 메뉴를 모두 통합한 것도 아니다. 03/04 기능의 로컬 구현과 실제 데이터의 계정 연결은 별개다. 최신 서버 코드가 정책을 읽어 요청을 제한하며 원격 앱 배포는 수행하지 않았다.

아래 판매 건수·금액·재고의 동일성은 **원본 보존 결과**다. 모든 화면이 새 관계를 사용한다는 뜻으로 해석하지 않는다. 메뉴 전환의 확정 원칙과 후속 구현 순서는 [메뉴 재배치 가이드](07-navigation-and-permissions.md)를 따른다.

## 적용과 보존 대조

1. 실제 DB를 읽기 전용으로 조사하고 기존 7월/12월 행사·46개 재고가 02 이관 기록과 같음을 확인했다.
2. `scripts/retireLegacyContracts.mjs --prepare`로 원본/관계/스키마와 다른 계정 지문을 새 파일에 백업했다. 로그인 비밀번호/해시·이메일·토큰·DB 연결 설정은 저장하지 않았으며 인증 주체는 ID·탈퇴 표식만 포함한다.
3. 백업을 독립 PGlite에 복사하여 원본 지문 대조 → 종료 → 동일 명령 재전송 → 호환 복구 → 원본 무변경을 통과했다. 이 복사는 종료 계약 재현용이며 실제 DB의 모든 FK/트리거·이미지 파일·브라우저 큐를 복원한 실험은 아니다.
4. 통과한 백업/재현 결과와 사용자 기기 확인을 요구하는 `--apply`를 실행했다. 보관 계정 잠금, 최신 원본/관계/다른 계정 지문 비교, 계약 정책/명령 영수증을 한 트랜잭션으로 저장했다. 종료 정책은 version 1, `legacy_writes_closed=true`다. 커밋 시각은 2026-10-22 17:54:36 KST다.
5. 커밋 후 별도 읽기 전용 연결의 `--verify`에서 정책/영수증·원본·관계·다른 계정을 대조했다. `verified`, `sourceUnchanged`, `otherAccountsUnchanged`가 모두 true다.

## 백업·실행 보고서

Git 제외 경로 `.local-archive/contract-retirement-2026-10-22-verified/`에 보관한다.

- `before.json`: 원본/관계/스키마·본인 및 다른 계정 대조 지문.
- `rehearsal.json`: 복사 DB 종료/재전송/복구 성공과 실제 적용할 명령.
- `applied.json`: 실제 정책 적용과 원본 보존 대조·커밋 결과.
- `verified.json`: 커밋 후 독립 읽기 전용 대조 결과.

처음 준비한 `.local-archive/contract-retirement-2026-10-22/before.json`은 재현 중 JSONB 객체 키 순서 비교 문제를 발견한 시도의 백업이다. 값별 비교로 고친 뒤 새 백업/재현부터 다시 통과했으며, 첫 시도에서는 실제 정책을 변경하지 않았다. 기존 백업 파일을 덮어쓰지 않는다.

## 검증과 남은 작업

- 전체 `npm test` **159개 통과**, `npm run build` 통과. 기존 청크 크기와 Tailwind 플러그인 소요시간 경고는 유지한다.
- 새 도구 회귀는 인증 정보 제외·준비 단계 실제 스키마 무변경, 백업 파일 충돌 시 원본 보존, 미확인 기기/재현 불일치/대상 변경 거절, 영수증 실패의 정책 롤백·같은 백업 재시도를 검증했다. 기존 02 이관 도구 회귀도 통과했다.
- 실제 DB의 추가 DDL은 계약 정책/명령 테이블이다. 03/04 테이블은 해당 기능의 기존 명시적 API 초기화 규칙을 유지한다. 실제 작가 계정 연결·행사 일정 추정·재고 수량 변경은 하지 않았다.
- 정책을 읽고 410을 반환하는 것은 06 서버 코드다. 원격 앱을 새로 배포한 것은 아니며, 오래된 배포 코드가 새 DB 플래그를 강제로 준수한다고 간주하지 않는다. 공개 전 서버/클라이언트를 같은 계약으로 반영해야 한다.
- `admin_id`·이름 별칭·ID 매핑은 재고/원장/백업 읽기가 사용하는 활성 참조다. 물리 삭제는 별도 저장 형식 이관과 참조 교체 전까지 미완료다. 삭제나 과거 백업 덮어쓰기로 종료를 복구하지 않는다. [06 복구 절차](06-implementation.md)에 따라 정책만 다시 연다.
- 실 PostgreSQL 다중 연결 경쟁·실제 브라우저/모바일/Android·배포 캐시 검증은 미실행이다. 실제 DB는 보존 대조/전환에만 사용했고 판매·파손·지급 등의 테스트 데이터를 넣지 않았다.

## 도구 실행 계약

`--prepare`, `--apply`, `--verify` 모두 명시적 `--admin-id`, `--directory`를 요구한다. 연결 설정은 `--env-file`로 서버 파일에서 읽는다. 준비는 읽기 전용 트랜잭션이며 적용은 `--queues-confirmed --latest-client-confirmed`와 일치하는 백업/재현 결과가 필요하다. 이 확인 플래그는 서버가 관측한 사실이 아니라 사용자의 확인을 실행자가 반영하는 것이다.

준비/적용/검증 결과 파일은 새 경로에만 생성한다. 적용 중 저장/검증 실패는 커밋 전에 롤백하며, 커밋 후 보고서 저장 실패는 별도 오류로 구분한다. 같은 실행을 무작정 반복하지 말고 저장된 영수증과 읽기 전용 검증 결과로 적용 여부를 먼저 확인한다. 기존 공개 API의 현재 비밀번호 검증은 유지하며 이 도구는 명시적으로 승인된 DB 관리 작업용이다.
