# 02 호환 기반 구현·검증 기록

기준일: 2026-10-22. 아래는 호환 기반 구현 기록이다. 후속 사용자 요청으로 기존 실제 자료 이관을 완료했으며 [이관 결과](02-data-migration.md)에 원본 대조와 백업을 기록했다. 앱 배포는 수행하지 않았다.

## 구현한 계약

기존 상품·행사·판매 테이블을 계속 수량/금액의 기준으로 사용하고, 별도 관계 테이블로 부스·소유자·작가 후보·수취인을 연결한다. 기존 열/복합 키와 과거 스냅샷은 제거하거나 재계산하지 않는다. 정산 이름 키는 호환용 별칭으로 유지하고 새 API는 영구 recipientId로 대상을 지정할 수 있다. 구형 경로 제거는 06이다.

- `api/lib/boothFoundation.js`: 추가 스키마, 결정적인 레거시 ID, 원본 스냅샷/지문, 기본 부스 이관·반복 실행, 공통 권한, 공동 총재고 수정·감사 영수증, 수취인/상품 귀속 매핑.
- `api/booths.js`: 자기 계정의 명시적 미리보기/이관/검증 및 권한 있는 소유자 재고 조회·수정. 요청의 adminId로 이관 대상을 바꾸지 않는다.
- `api/pos.js`: 명시적 boothId 또는 이관된 기본 부스에서 역할·행사 범위를 검사한다. 비밀번호는 보관용 레거시 계정이 아닌 실제 호출자의 비밀번호로 확인한다.
- `api/settlements.js`, `api/lib/eventSettlement.js`, 정산 공통 계산: recipientId와 기존 별칭 연결, 이름 변경 후 비용 참여자 분할 방지, 확정 금액과 영수증 보존.
- `api/product-images.js`, `scripts/local/images.mjs`: 부스 권한과 원본 상품 수정 권한을 검사하고 기존 이미지 경로/파일을 보존한다.
- `api/lib/accountInventory.js`: 이관 계정은 서명된 v2 백업에 새 관계·초기 위치·이관/취소·재고 감사 이력을 포함한다. 공유 자료의 계정 전체 교체 복원은 거절한다. 미이관 계정의 v1 왕복은 유지한다.
- `src/database/*`, `src/sync/syncService.ts`, `src/hooks/useSync.ts`, `src/App.jsx`: IndexedDB v4, 새 주문의 작성자/부스/프로토콜 문맥, 구형 큐 보존, 계정이 다른 캐시 열람/재전송 차단, 서버 권한 거절 시 캐시로 판매를 재개하지 않음.
- `src/pages/AccountPage.jsx`, `src/components/AccountBackup.jsx`: 서버의 복원 제한을 기존 화면에 반영. 임의의 성공 안내나 새 납품 화면은 추가하지 않는다.
- `vite.config.js`: 로컬 `/api/booths` 연결. 운영의 파일 기반 API 라우트와 같은 계약이다. SW v131.

추가 FK는 이력 보존 대상에 CASCADE 삭제를 붙이지 않는다. 같은 이름의 다른 계정은 서로 다른 ID다. 이관 후보의 kind는 unverified이고 계정 연결은 하지 않는다. 이름별 후보를 생성했다는 사실을 실제 소유권 검증으로 해석하지 않는다.

## 이관 API와 적용 방법

아래 요청은 사용자 API 계약 설명이다. 후속 실제 이관은 백업과 복사 DB 재현을 거친 관리 CLI로 수행했다. 기존 POS 스키마가 초기화된 별도 DB에서 먼저 수행한다.

1. `POST /api/booths`의 `action: previewLegacy`: 자기 계정의 원본 건수·수량·판매·차감·지급·마감 지문 및 예외를 반환한다. 새 관계 테이블이나 이관 레코드를 만들지 않는다.
2. `action: migrateLegacy`, `payload: { password, expectedFingerprint }`: 현재 비밀번호와 최신 미리보기 지문을 확인하고 같은 트랜잭션에서 추가 관계를 만든다. 데이터가 바뀌면 409이며 다시 미리보기한다.
3. `action: verifyLegacy`: 현재 원본 보고서를 반환한다. 최초 이관 원본은 별도 저장하여 이후 정상 거래까지 원복하지 않는다.
4. 실패는 전체 rollback한다. 같은 원본으로 다시 실행해도 부스·초기 재고·수취인·원본 이력을 중복 생성하거나 회수된 참여 권한을 재활성화하지 않는다.

일반 POS 조회로 계정을 자동 이관하지 않는다. 미이관 계정은 기존 흐름을 유지하고, 이관 완료 계정만 새 권한/보존 정책을 사용한다. 새 작가 가입/초대/부스 생성 UI는 03이다. 운영자·작가 관계를 임의 SQL로 만들어 서비스에서 사용하라는 뜻이 아니다. 테스트에서만 역할/연결 관계를 fixture로 주입했다.

## 공동 총재고 API

- `GET /api/booths?ownerId=...&boothId=...`: 활성 부스 owner/manager에게 해당 참여 작가의 상품별 총재고·창고·수정 버전·사용 불가 수량만 반환한다. 다른 부스명·행사별 배정·원가·매출을 보내지 않는다.
- boothId 없이 ownerId를 조회하면 실제 소유자 관리 관계가 있는 본인만 허용한다.
- `POST /api/booths`, `action: adjustOwnerStock`, payload는 ownerId, inventoryId, 선택 boothId, UUID requestId, version, totalStock, reason(receipt/correction)이다.
- 같은 요청은 동일 결과, 내용이 다른 같은 ID와 오래된 버전은 409다. 판매·기존 차감·행사 배정 아래로 줄일 수 없고 행사 배정 자체는 수정하지 않는다. 참여 종료된 부스와 seller/viewer는 수정할 수 없다.
- 수정자·근거 부스·이전/이후 수량·사유·서버 시각을 영수증에 보존한다. 기존 POS 재고 쓰기도 같은 감사 원장에 변경 전후 수량을 기록하며 참여 종료 후 총재고 수정/추가 배정으로 우회할 수 없다. 복수 부스·기존 POS 쓰기는 같은 레거시 보관 계정/상품을 기준으로 직렬화한다.
- 기존 ID가 한 소유자의 여러 원본 계정에서 중복되면 임의로 대상을 고르지 않고 거절한다. 03에서 연결 화면을 만들 때 명시적 원본 상품 식별자를 확장할 수 있다.

## 구형 주문과 캐시

새 주문은 protocolVersion 2, actorId, 가능한 boothId를 payload와 저장 행에 기록한다. 서버가 인증된 작성자·부스·행사·revision·마감을 다시 검사한다. 상품 귀속 ID는 서버 매핑에서 가져오며 클라이언트의 임의 소유자/수취인/정산 별칭을 신뢰하지 않는다.

구형 큐의 localOrderId·payload·생성 시각·불명확 상태는 변경하지 않는다. 구형 요청은 원래 레거시 계정으로만 처리한다. 새 작성자가 있는 주문은 다른 계정/부스에서 자동 재전송하지 않는다. 부스 ID가 없던 이관 전 자기 계정 주문은 ID를 유지한 채 원래 기본 부스로 전송한다.

계정 정보가 없는 구형 캐시는 오프라인에서 임의 사용자에게 보여주지 않는다. 원래 계정의 인증된 서버 응답을 한 번 받은 뒤 미전송 투영을 보존하면서 캐시의 계정 문맥을 연결한다. 업그레이드 직후 완전 오프라인이면 온라인 확인이 필요하지만 원 주문과 캐시는 삭제하지 않는다. 다른 계정의 미전송 투영은 새 서버 응답으로 덮어쓰지 않는다.

## 전환 중 제한과 후속 작업

- 수량의 기준은 기존 원본 테이블이다. 초기 위치/원장 투영은 재고를 추가 입고하거나 새 납품으로 차감하지 않는다. 기존 창고가 실제 작가 보관인지 부스 보관인지는 임의 추정하지 않는다. 작가 창고→부스 보관→행사의 실물 이동·예약·반환은 04에서 구현한다.
- 새 소유자·수취인 ID가 있어도 기존 계정이 곧 작가라는 가정은 하지 않는다. 미확인 소유권·동명이인·불완전 세트/판매 원본은 03 연결 전에 확인해야 한다.
- v2 백업은 현재 이관 자료를 보존하는 용도다. 공유 상태를 과거 시점으로 일반 복원하는 기능, 구형 백업의 독립 서비스 DB import, 소유권 승계·종료/탈퇴 해제 workflow는 제공하지 않는다. 이관 계정의 restoreAccount/deleteAccount/deleteProject/clearSales는 409다.
- 기존 계정/행사 잠금을 보존해 호환 정확성을 우선한다. 매 요청에서 전체 계정 매핑을 확인하므로 대규모 데이터의 성능과 실제 PostgreSQL 잠금 경쟁은 별도 확인이 필요하다. 성능 개선 때 원본 스냅샷 보존과 영수증 원자성을 유지해야 한다.
- 실제 PostgreSQL 다중 연결, 브라우저/다기기 오프라인, Android/배포 캐시 검증은 이 기록에서 자동 통과로 간주하지 않는다.
- 사용자 확인상 서비스는 운영 전이며, 기존 실제 admin 자료 이관을 완료했다. 다른 계정 자료는 유지했다. 앱 배포·커밋·푸시·PR은 수행하지 않았다. 다중 사용자 공개 운영의 준비 완료 판정과는 구분한다.
