# 03 작가 연결 구현 기록

2026-10-22. 로컬 변경이며 기존 실제 DB 자료에 초대를 발급하거나 계정을 연결하지 않았다. 실제 자료 이관 결과는 [02 기록](02-data-migration.md)을 따른다.

## 화면과 권한

마이페이지의 작가·부스 영역에서 개인 작가 프로필과 첫 기본 부스를 만든다. 가입 단계에 영구 계정 유형을 추가하지 않는다. 기존 이관 부스 운영자는 미연동 작가를 추가하거나 기존 후보 프로필의 초대 코드를 발급한다. 수신자는 가입/로그인 후 같은 영역에 코드를 입력하고 부스·작가·만료를 확인한 뒤 총재고 공동 관리에 동의하여 연결한다. 코드를 메시지로 보내는 기능은 없으며 운영자가 전달한다.

참여 작가 연결은 `pos_booth_artists` 관계이며 부스 운영 역할인 `pos_booth_members`를 생성하지 않는다. 작가가 자기 이력을 조회해도 부스의 전체 POS·정산에 접근할 권한은 생기지 않는다. 기존 공동 총재고 API는 연결된 작가와 참여 중인 부스 owner/manager 모두 허용한다. 참여 종료 후 부스의 재고 변경 권한은 종료되지만 작가 본인 과거 이력 조회는 유지한다.

계정당 신규 기본 부스 1개를 제공하는 02 저장 범위를 유지한다. 기존 자료가 있는 미이관 계정은 새 부스 생성으로 자료를 자동 이관하지 않고 명시적 이관을 요구한다. 여러 부스에서 각각 승인받은 프로필을 한 계정에 연결할 수 있지만 물리 소유자/상품/재고 ID는 합치지 않는다. 여러 부스 신규 생성과 운영 화면의 작업 부스 선택은 후속 범위다.

## 서버 계약

인증된 `/api/booths` 요청만 사용하며 사용자 ID를 요청 본문에서 받지 않는다.

| 요청 | 동작 |
| --- | --- |
| GET `?artists=home` | 본인 연결 프로필·운영 역할·연결 출처·복원/탈퇴 제한 |
| GET `?artists=history` | 위 항목과 본인 귀속 행사별 판매·취소·예상/확정 정산·지급 |
| GET `?artists=participants&boothId=…` | 활성 owner/manager만 해당 부스의 프로필·초대 메타데이터·감사 기록 |
| POST `createArtistProfile` `{name}` | 부스와 독립된 본인 프로필. 계정별 결정 ID로 재시도 중복 생성 방지 |
| POST `createFirstBooth` `{name}` | 프로필이 있고 기존 재고/행사가 없는 계정의 첫 부스와 owner 역할 생성 |
| POST `createBoothArtist` `{boothId,name}` | 운영자가 미연동 후보 추가. 이름만으로 실제 계정과 연결하지 않음 |
| POST `issueArtistInvitation` `{boothId,profileId}` | 출처 부스 운영자가 미연동·proxy 후보 초대. 미지정 프로필은 소유자 확인 전 발급 차단 |
| POST `previewArtistInvitation` `{token}` | 로그인한 수신자에게 연결 대상과 만료 확인 |
| POST `acceptArtistInvitation` `{token,acceptSharedStock:true}` | 프로필 연결·소유자 관리 관계·참여 상태·초대 사용·감사를 한 트랜잭션으로 반영 |
| POST `revokeArtistInvitation` `{boothId,invitationId}` | 발급 부스 운영자가 미사용 초대 철회 |

POST 형식은 `{action,payload}`다. 초대는 무작위 32바이트 코드, SHA-256 해시 저장, 7일 만료다. 원문은 발급 응답에 한 번만 제공하고 DB/조회/백업/로그에 포함하지 않는다. 재발급 시 미사용 이전 코드를 철회하고 감사를 남긴다. 만료/철회/참여 종료/발급자 권한 회수 시 신규 연결을 거절한다. 동일 계정의 수락 재시도는 이미 연결된 결과를 반환하고 타 계정 재사용은 거절한다.

잠금 순서는 호출자·레거시 보관 계정·발급자 계정의 정렬 잠금 → 부스 → 프로필 → 초대다. 반복 읽기 트랜잭션 충돌/교착/유일성 충돌은 409이며 실패 트랜잭션은 전부 롤백한다. 실제 다중 연결 경쟁은 별도 검증이 필요하다.

## 데이터와 열람 범위

`pos_artist_invitations`, `pos_artist_link_audit`를 추가하고 `pos_stock_owners.origin_booth_id`만 nullable로 확장해 개인 프로필을 부스 없이 생성한다. 기존 출처·ID는 바꾸지 않는다. 03 최초 요청 시 추가 스키마를 초기화하고 이후에는 존재 확인으로 DDL을 생략하며 일반 POS 조회로 기존 계정을 자동 이관하지 않는다. 레거시 POS 기본 테이블은 기존 앱 초기화 경로를 사용한다.

연결은 프로필의 linked_user_id/status, 소유자 kind, owner_members와 참여 상태만 바꾼다. 원본 상품·창고·행사 수량·판매·차감·지급·마감에는 쓰지 않는다. 연결 감사에는 프로필·부스·발급/수락 계정·초대 ID·시각을 보존한다. 기존 재고 변경 감사는 그대로 유지한다.

본인 조회는 승인된 owner_id → recipient_id → 행사별 고정 별칭으로 제한한다. 서버 안에서 기존 정산 엔진으로 비용을 배분하되 응답은 본인 행만 추린다. 공동 세트의 다른 상품/작가·세트명·주문 총액·결제 수단·전체 행사 비용·운영 메모·송금 메모는 반환하지 않는다. 본인 비용의 이름/귀속 금액과 지급 날짜/금액만 표시한다. 마감은 저장된 snapshot.rows를 사용하고 현재 마스터/비용으로 재계산하지 않는다. 원본을 보존한 취소 이력도 본인 구성품만 반환하며 취소 금액을 현재 정산에 합산하지 않는다. 옛 취소 원본이 없는 tombstone은 임의 복원하지 않는다.

부스 백업 v2에는 부스 참여 개인 프로필/소유 관계도 포함한다. 초대 메타데이터와 연결 감사는 보존하되 원문 코드와 token_hash는 제외한다. 이 백업으로 초대를 다시 활성화하는 복원 기능은 제공하지 않는다. 연결 후 화면의 복원·탈퇴 제한도 갱신한다. 개인 작가 전용 전체 백업/복구는 후속 데이터 수명 작업이다.

## 오류 정정 절차

1. 작가는 부스 운영자에게 프로필·부스·행사와 문제가 있는 판매/비용/지급 항목을 전달한다. 연결 화면의 출처/작성 계정과 기존 원본·재고 감사 기록을 함께 확인한다.
2. 아직 수락 전이면 운영자가 초대를 철회하고 실제 소유자를 확인해 다시 발급한다. 미지정 상품을 임의의 작가에게 배정하거나 동명이인 프로필을 자동 병합하지 않는다.
3. 잘못 수락한 연결은 일반 화면에서 해제·재연결하지 않는다. 양쪽 본인 확인과 백업을 먼저 확보하고 별도 복구 작업에서 관계만 정정한다. 새 감사 기록을 남기고 원래 연결 출처/거래·확정 마감은 덮어쓰지 않는다.
4. 거래 정정은 기존 취소/지급 취소/마감 해제 조건을 따르는 별도 운영 작업이다. 신고 접수만으로 과거 금액을 바꾸지 않는다. 자동 분쟁 처리·프로필 병합 UI는 제공하지 않는다.

## 검증

- 전체 `npm test`: 143개 통과. 마지막 취소 열람·백업 포함 범위 보완 후 기반/작가 화면 14개 재확인 통과.
- 초대 발급 권한/원문 비저장/동의/동일 계정 재시도/타 계정 재사용 거절, 만료·철회·재발급·권한 회수·참여 종료, 중간 실패 전체 롤백 후 재시도 검증.
- 연결 전후 원본 전체 지문 일치, 본인과 부스 운영자의 공동 재고 권한 유지, 전체 부스 접근 차단, 다른 부스의 같은 이름 프로필을 별도 승인으로 연결하는 회귀 검증.
- 세트 공동 판매의 본인 구성품만 반환, 표시명 변경·참여 종료 후 조회, 예상/확정 구분·확정 스냅샷 보존·부분 지급/미지급·취소 이력 비공개 정보 제거 검증.
- 화면 모형: 코드 확인 후 동의해야 수락 버튼 활성화, 코드 변경 시 이전 확인/동의 폐기, 성공 후 코드 제거. 초대 코드는 URL/로그인 저장소에 저장하지 않는다.
- `npm run build` 통과(기존 500kB 청크 경고). 최종 프런트 변경 후 빌드/관련 14개 회귀 재확인 통과. 스키마 존재 확인 최적화 후 기반 13개도 재확인했다. `git diff --check` 통과.
- 미실행: 실제 PostgreSQL 다중 연결 경쟁/부하, 실제 브라우저·모바일의 두 계정 왕복, 배포 SW 교체. 이번 작업은 실제 DB를 검증용으로 사용하지 않았다.

## 수동 확인 순서

로컬 별도 DB의 두 계정에서 운영자 마이페이지 → 참여 작가 초대 발급 → 작가 계정 로그인 → 코드 확인/동의 수락 → 본인 행사 정산 확인 순서로 확인한다. 작가가 직접 부스 전체 API에 접근하면 403이어야 하고, 운영자는 연결 뒤에도 참여 작가 총재고를 관리할 수 있어야 한다. 기존 실제 자료의 미지정 4상품은 확인 전 그대로 두며 자동 연결하지 않는다.
