## 1. 사용자와 합의한 운영 구조

작가가 자기 계정으로 부스를 만들면 그 작가가 해당 부스의 운영자가 된다. 운영자는 다른 작가를 초대한다. 초대받거나 스스로 부스에 참여한 작가는 자기 재고를 행사에 직접 배정한다. 납품 승인 절차는 사용하지 않는다. 한 작가가 여러 부스에 참여하거나 다른 부스를 운영할 수 있다.

**참여 중인 작가의 총재고는 작가 본인과 해당 부스 운영자가 모두 관리할 수 있다.** 참여 작가가 다른 참여 작가의 재고를 관리할 권한까지 자동으로 얻지는 않는다. 미가입 작가는 운영자가 대신 프로필·상품·재고를 등록하고, 나중에 계정과 연결한다.

상품 정보는 상품명·이미지·굿즈 종류·기본 가격·원가 등의 원본 정보다. 부스 판매 설정은 행사 판매가·세트·배정 수량이다. 이 둘과 재고 소유권은 별개다. 부스를 만들었다고 다른 작가 상품의 소유권을 얻는 것은 아니다.

## 3. 역할과 권한표

부스 생성자는 owner다. manager는 owner가 지정한 공동 운영자다. seller는 판매 담당자이며 viewer는 운영 조회 담당자다. 작가 참여는 부스 운영 역할과 별도 관계다. 작가는 자기 부스 owner이면서 다른 부스 참여 작가일 수 있다. 조직 관리자는 조직 소유자 자원에 대해 작가 본인과 같은 소유자 관리 권한을 가진다.

| --- | --- | --- | --- | --- | --- |
| 자기 상품·원가·이미지 관리 | 가능 | 타 작가 원본은 별도 위임 필요 | 별도 위임 필요 | 불가 | 불가 |

명시적 위임이 없는 작업은 거절한다. 여러 역할을 겸하면 허용 범위를 합치되 마감/재고/자원 범위 제한은 항상 적용한다. 권한은 서버에서 확인하며 프런트엔드 메뉴 숨김으로 대체하지 않는다.

### 총재고 공동 관리의 범위

- 활성 작가 참여 관계가 있는 부스의 owner/manager는 작가의 총재고와 재고 수정을 위한 수량 요약을 조회한다. 총재고는 부스마다 복사하지 않고 같은 소유자 상품의 공동 기준으로 둔다.
- 타 부스의 수량은 총 배정·판매/차감 합계로만 제공한다. 상대 부스명·행사명·판매 금액·고객/결제·다른 상품 목록은 노출하지 않는다.
- 총재고 수정 권한이 다른 부스 배정 수정·소유자 변경·판매 취소 권한을 의미하지 않는다.
- 증가분은 원칙적으로 작가 창고 입고/정정으로 기록한다. 행사에 새로 등록한 물품은 작가 입고와 행사 배정을 연결한 원자 작업으로 한 번만 계상한다. 재고 정정은 실제 이동을 대신하지 않는다.
- 감소는 미배정 가용분에서만 가능하다. 다른 위치의 로스는 그 위치의 권한으로 처리한다. 이미 판매·차감·배정된 분을 총재고 편집으로 지우지 않는다.
- 수정자 사용자 ID, 권한 근거 부스 ID, 이전/이후 수량, 사유, 요청 ID, 서버 시각을 남긴다. 작가가 자기 재고 변경 이력을 볼 수 있어야 한다.
- 참여 종료 시 그 부스를 통한 작가 총재고 신규 수정 권한은 즉시 회수한다. 부스에 남은 위탁품은 반환·정산을 위한 제한된 정리 권한으로 관리한다.
- 작가가 초대 수락할 때 운영자의 총재고 공동 관리 범위를 확인할 수 있게 한다. 미연동 프로필을 계정에 연결해도 이 운영 방식은 유지한다.

## 4. 직접 재고 관리와 행사 기간 제한

2026-10-22 사용자 추가 지침이 초기 예약/납품 승인 설계보다 우선한다. 요청·수락·거절·취소·예약 UI/상태를 만들지 않는다. 기존 원본 재고 행을 작가 소유 ID에 연결하고 행사들은 같은 재고를 참조한다. 부스는 권한 범위이며 별도의 승인 단계/중간 물리 위치를 추가하지 않는다.

- 관리 총재고 T는 미배정 수량과 행사별 초기 배정, 알려진 창고 차감의 합이다. 현재 실물 Q는 미배정과 행사 잔량의 합이다. 판매 S·파손/분실/외부 차감 L·불완전 과거 차이 H를 구분해 T=Q+S+L+H를 대조한다. 원본 누적 입고는 별도다.
- 새 상품 20개를 행사에 직접 등록: 작가 T=20, 행사 초기/잔량=20, 미배정=0. 동일 수량을 두 번 입고하지 않는다.
- 기존 재고 50개 중 20개 배정: T=50, 행사 초기/잔량=20, 미배정=30. 수량 이동 때문에 누적 입고를 늘리지 않는다.
- 작가와 활성 부스 owner/manager가 총재고를 공동 관리한다. 행사의 배정은 미배정에서만 늘리고, 판매/차감된 수량보다 초기 배정을 줄이지 않는다. 타 부스 운영자는 다른 부스의 배정을 수정하거나 상세를 조회하지 못한다.
- 작가는 자기 상품을 참여 행사에 직접 설정한다. 행사 기간에는 해당 행사 배정·회수·가격·행사 로스 변경을 거절한다. 운영자는 계속 관리한다. 개인 미배정 수량의 입고/정정은 행사 잔량을 바꾸지 않는 범위에서 유지한다.
- 날짜 구현 기준(설계 채택): 운영자가 시작일·종료일을 입력하고 한국 시간의 양끝 포함 기간으로 검사한다. 일정 미설정 행사는 운영자만 수정한다. 기존 행사 이름에서 날짜를 추측하지 않는다. 자기 부스 owner/manager인 작가는 운영 역할로 관리할 수 있다.
- 미판매 회수/행사 간 이동은 같은 원장의 수량 이동이다. 판매 취소는 원래 행사와 구성으로 복원하며 마감은 거절한다. 반환 뒤 취소되어도 원래 행사에 복원하고 미배정에 중복 가산하지 않는다.
- 파손/분실/외부 판매는 위치·소유자·수량·작성자를 기록하며 매출/송금·정산 차감을 자동 생성하지 않는다.
- 참여 종료는 잔량·미지급이 있으면 ending으로 두고 신규 배정/대리 총재고 변경/판매를 막는다. 기존 잔량 회수·정산과 본인 과거 열람은 보존한다. 정리 후 재확인하여 ended로 바꾼다.

예: T=100에서 A 행사 40/B 행사 20이면 미배정 40. B에서 5개 판매하면 Q=95, S=5, T=100. 미판매 15개 회수 후 판매 5개를 취소하면 원래 B 행사에 5개가 복원되며 Q=100이다. 같은 상품의 동시 수정은 보관 계정/상품/행사 잠금과 version으로 검사한다.

## 5. 판매·정산·조회 정책

- 신규 거래는 상품 소유자 ID와 정산 수취인 ID를 서버의 승인된 연결에서 결정한다. 클라이언트가 보낸 작가 이름/ID만으로 귀속하지 않는다.
- 공동 제작자 표시는 복수일 수 있지만 초기 모델의 상품 재고 소유자와 수취인은 하나다. 공동 제작자 간 내부 분배는 후속 범위로 두며 세트는 구성 상품별 수취인을 가진다.
- 행사 가격·세트·비용 변경은 부스 운영자가 기록하고 자기 상품에 귀속된 내역을 작가에게 공개한다. 기존 확정 스냅샷과 지급 기록은 변경하지 않는다.
- 세트 판매액 배분은 현재 구성 수량·기준 단가의 가중치와 원 단위 최대 나머지 방식을 유지한다. 새 모델에서는 계산에 사용한 기준·배분액·수취인 ID까지 고정하고 동률 순서를 저장해 재계산 차이를 막는다.
- 행사 공통 비용의 정액/정률·균등/매출비례, 매출 0원의 균등 대체, 음수 정산금은 현재 규칙을 유지한다. 비용·개별 차감·지급·지급 취소를 구분한다.
- 참여 프로필이 여러 개여도 계정 연결 때문에 과거 비용 분담 단위를 합치거나 정산을 다시 나누지 않는다. 기존 이름별 수취인 단위를 보존하고 작가 계정은 승인된 단위를 합산 조회한다.
- 마감은 미동기화 확인과 서버 최신 미리보기 비교 후 확정한다. 마감 중 판매/취소/배정 변경은 거절하고, 지급 잔액이 있으면 지급 취소 전 마감 해제를 거절한다.
- 판매 취소는 원본 거래를 보존하는 취소 기록 방향으로 전환한다. 현재 구현은 판매 행을 제거하고 영수증을 남기므로 과거 삭제된 거래 내용을 새로 복원했다고 주장하지 않는다. 취소 영수증만 남은 경우 그 사실을 이관한다.
- 작가 조회는 자기 수취인 행만 서버에서 추출한다. 여러 작가가 포함된 세트/거래의 다른 항목, 부스 전체 매출·비용, 다른 작가 원가를 그대로 전송하지 않는다. 공동 총재고 권한도 다른 부스 매출 열람 권한은 아니다.
- 판매·정산 기록은 실제 입금 확인/송금·PG 승인과 다르다. 실지급 잔액과 판매액을 같은 수익 수치로 혼합하지 않는다.

## 6. 미연동 작가와 계정 연결

- 운영자가 만든 임시 작가는 생성 부스 범위에서만 관리한다. 같은 이름을 다른 부스에서 발견해도 자동 연결하지 않는다.
- 만료·철회 가능한 1회용 초대를 로그인 계정이 수락한다. 초대 대상 프로필/부스·대리 관리 범위·기존 자료가 무엇인지 확인할 수 있어야 한다.
- 연결은 소유자/프로필의 관리 관계를 연결한다. 기존 주문을 새 계정의 주문으로 다시 만들거나 재고를 새로 입고하지 않는다.
- 한 계정이 여러 미연동 프로필을 승인받아 연결할 수 있다. 서로 다른 재고는 증빙 없이 같은 재고로 합치지 않는다. 02/03은 물리 병합을 제공하지 않는다.
- 연결 해제·오연결 정정은 온라인 감사 작업으로 남기고, 활성 자산/정산이 있으면 근거 확인 없이 다른 계정에 재연결하지 않는다.
- 연동된 작가 상품 정보는 기본적으로 작가가 관리한다. 총재고는 P02의 공동 관리 대상이며 상품 정보 수정 위임과 구분한다. 미연동 작가의 상품 정보는 운영자가 대리 관리한다.

백업은 개인 소유 자원과 부스 자원으로 구분한다. 개인 자료 내보내기는 본인, 부스 전체 백업·복원은 owner만 가능하다. 공유 거래/재고/정산을 과거로 덮어쓰는 일반 복원은 02에서 열지 않는다. 우선 백업·검증/변환을 지원하고 복구는 자원 관계를 검증한 별도 절차로 둔다. 이 제한은 현행 계정 전체 교체 복원에서 변경되는 계약이므로 02 구현 때 API·화면·하네스에 함께 반영한다.

구형 서명 백업은 원본 소유자/형식/버전을 검증하고 별도 DB/격리된 변환 단계에서 매핑한다. 서명 검증을 위해 원본 파일은 수정하지 않는다. 이미지 URL과 파일 자체는 구분하며 참조가 남은 이미지를 계정/부스 종료만으로 삭제하지 않는다. 복원/이관은 요청 영수증·새 revision·원자성·재실행 검사를 유지한다.

## 9. 구형 큐·권한 회수·경쟁 처리

- 큐를 새 부스에 복사하거나 localOrderId를 재발급하지 않는다. 서버가 소유 행사로 확인한 projectId의 유일 매핑만 적용한다. 구형 큐에 사용자 ID가 없다면 현재 로그인만으로 작성자를 추정하지 않는다.
- 구형 요청은 원래 계정과 그 계정 기본 부스의 원래 행사로만 허용한다. 신규 공동 운영자는 인증된 새 문맥을 사용한다. 구형 호환을 새 멤버십 검사 우회로 쓰지 않는다.
- 신규 큐는 생성 사용자·boothId·projectId·revision·프로토콜 버전을 저장한다. 사용자나 부스를 바꿔도 원 큐의 작성 주체가 바뀌지 않는다.
- 동기화 시 현재 권한과 revision/마감 상태를 재검사한다. 권한 회수·마감·이관 충돌은 구분 가능한 오류로 반환하고 원 큐를 보존한다. 권한을 복구하거나 운영자가 원본을 검토하는 복구 경로를 둔다. 다른 사용자 자동 재전송은 금지한다.
- 같은 논리 명령의 재시도는 동일 영수증과 fingerprint로 처리하고 변경된 내용의 같은 ID는 거절한다. 새 거래의 영수증 범위는 부스/행사와 명령 ID이며 사용자별로 중복 판매를 허용하지 않는다. 레거시 영수증도 확인한다.
- 계정 활성/멤버십 → 소유자 상품(정렬된 ID) → 부스/행사(정렬된 ID) → 영수증/세부 행의 공통 잠금 순서를 설계 기준으로 삼는다. 모든 쓰기·권한 회수·마감·복원이 같은 순서를 사용해야 한다. 실제 SQL 잠금 방식은 02에서 정하고 PostgreSQL 다중 연결로 검증한다.
- 판매 후 취소의 큐 순서, 응답 유실 시 동일 ID 재시도, 다중 탭 Web Locks, 종료 후 SYNCING 복구를 유지한다. 서버 수량 경쟁을 브라우저 잠금만으로 해결하지 않는다.

## 10. 02 작업 순서·전환·검증 계획

1. 스키마 확장과 명시적 ID/레거시 매핑을 추가한다. 현재 열·키·정산 스냅샷을 먼저 제거하지 않는다.
2. 별도 DB에서 기본 부스·소유자 후보·행사/재고/수취인 매핑 dry-run을 실행한다. 원본 수와 합계·예외 보고를 보존한다.
3. 재실행 가능한 backfill과 공통 권한을 연결한다. P02 공동 총재고 권한도 테스트한다. 사용자 확인 없는 후보를 실제 작가 소유로 확정하지 않는다.
4. 정산 ID·삭제/복원 보호·이미지/CSV 조회·구형 큐 호환을 같은 기반 단계에서 완료한다. 작가 초대와 신규 납품 UI는 열지 않는다.
5. 전환 중 기준 쓰기는 하나만 둔다. 구형 경로도 같은 자원 명령을 사용하게 하고 이중 차감/이중 지급을 막는다. API 버전·SW·Android 지원 범위를 명시한다.
6. 실제 전환 전 모든 기기 쓰기를 멈추고 동기화 상태를 확인한다. 서버는 오프라인 기기를 전부 알 수 없으므로 늦게 온 요청을 보존·분류할 복구 경로를 유지한다.
7. 실패 시 새 거래 전에는 검증된 복원, 새 거래 후에는 역매핑/전진 복구를 적용한다. 새 거래를 버리는 단순 스냅샷 복원은 하지 않는다.

## 11. 미확정 항목과 단계 진입 판정

02의 로컬 스키마·매핑·권한·보존 구현을 막는 정책 항목은 없다. 사용자 확인 P01/P02와 설계 채택 P03~P14를 기준으로 진행한다. P15는 04 사용자 추가 지침으로 확정했고 승인 절차를 제거했다. P16은 실제 개인정보 파기/운영 정책의 조건이며 이를 확정하지 않고 파기 기능을 열지 않는다. 구체 테이블명·API 형식·SQL 잠금 수단은 02의 구현 설계 산출물이다.

기존 운영 데이터의 실제 작가 소유권 판정과 마이그레이션 예외 해소는 별도 데이터 검토가 필요하다. 이 문서 작성으로 실제 데이터가 검증되거나 운영 전환이 승인된 것은 아니다.
